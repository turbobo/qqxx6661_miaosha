一句话主线:两条轴同时进化

策略线(接口内部怎么保证正确) 无锁 → 悲观锁 / 乐观锁 → 缓存一致性 V1~V5 → MQ 异步削峰 → Redis 预扣减 + 可靠入队
契约线(接口对外长什么样) 裸文本 → 统一包装 ApiResponse → 受理 + 轮询接口对 → messageId 单凭据 + 状态机
终点形态 接口不再是"做一个动作",而是"发起一个有状态的流程":grab 发起,status 观测。

演进主轴(4 步)

G0~G5 改内部、G6 改包装、G7~G8 改交互模式、G9 改为状态机入口。

1

实验期 G0–G5

接口"长相"几乎不变,变的全是接口内部:锁 → 缓存 → MQ。接口是策略实验的探针。

2

契约化 G6

JSON 请求体 + ApiResponse<T> 统一包装首次出现,错误从异常文本收敛为 code/message。

3

异步化 G7–G8

"受理接口 + 轮询接口"成对出现,requestId 成为查询凭据;状态词表逐步成型。

4

状态机化 G9

JWT + messageId 单凭据 + 订单状态机 + 全局降级态;幂等、补偿、对账全部挂在状态机上。

三条规律

把 10 代接口压缩成三句可以带走的话。

接口形态由一致性模型决定

要强一致,就同步返回结果;接受最终一致,就必须设计"受理 + 查询"接口对,并给出凭据——异步不是少做一步,而是多设计一个接口。

只要异步,必有凭据

messageId / requestId 是幂等、查询、补偿、对账四个机制的共同锚点。G5 返回"提交成功"却没有凭据,异步就等于失联——这是最贵的一课。

状态词表的收敛度 = 接口成熟度

从匹配中文文本,到固定枚举,再到与订单状态机一一对应;词表越收敛,前端、调用方与运维的沟通成本越低。
