核心思路：接口「秒回」，把重活丢给消息队列

之前的方案里，扣库存 + 建订单全部同步完成，接口 RT 直接暴露给用户。本方案把链路拆成两半：① 前台只把请求写进 RabbitMQ（同时用 Redis Set 记录「该用户已提交」，同一用户重复提交直接拦下），毫秒级返回「提交成功」；② 消费者线程在后台慢慢消费队列、扣库存、建订单。

你看到的「排队」其实是前端在轮询 purchase-result 接口：消费者处理完成后会把订单写入 USER_HAS_ORDER 缓存，轮询查到即宣告「抢购成功」。

实测：200 VUs 下 QPS 3944（悲观锁的 11.6 倍）、平均 RT 43ms（同步方案的 1/11）——瓶颈从接口转移到了消费速率。
体验一下：换一个 userId 点「提交订单」，接口几乎立刻返回；连续点「疯狂连点」，同一个 userId 只会成功一单，其余被「你已经抢购过了」拦下。
