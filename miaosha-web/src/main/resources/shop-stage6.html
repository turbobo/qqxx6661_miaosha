从「能卖」到「卖得稳」：工程化四件套

前面的方案解决了超卖、限流、缓存一致性问题；真正上线还要补齐工程化能力：① 分布式锁保证多实例部署时互斥依然成立；② 幂等保证用户连点、网络重试、MQ 重投都不会重复扣库存；③ 分布式令牌桶让限流配额跨实例共享（Guava 单机桶在集群下每台各放 10 个）；④ 熔断器在 DB 抖动时快速失败降级，防止故障扩散。

对比实验：② 号柜台点「新请求下单」后，立刻点「重复提交」——同一 requestId 被 SETNX 拦下；③ 号柜台 ×20 连点约一半拿到令牌（桶容量 10），其余被限流拦截；④ 号柜台可随时查熔断器当前状态（正常为 CLOSED）。
教学提示：下单会校验 userId 存在于 user 表（本环境已预置 id 1~2001 共 2001 个测试用户，换号下单可随意取用）——这正是真实世界的业务约束。
