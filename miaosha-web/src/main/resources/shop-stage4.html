五种双写策略 · 逐个下单对比

同一个商品（sid=16），用五种「缓存与 DB 的写入顺序」策略分别下单，观察各自的一致性缺陷。

V1 · 先删缓存再扣库

删除与扣库之间有窗口：读请求会把 DB 旧值回填缓存 → 脏数据

V2 · 先扣库再删缓存

业界基础策略：删缓存失败最多残留旧缓存，脏数据窗口极小

V3 · V1 + 延迟双删

异步 1 秒后二次删除，兜底清掉窗口期回填的脏缓存

V4 · V2 + 双删 + MQ 兜底

删缓存失败还发 delCache 队列由消费者重试删除，保证最终一致

V5 · 技术堆砌（反面）

乐观锁+用户校验+MQ+缓存三件套全上：架构不是越复杂越好

核心矛盾：缓存带来 3 倍吞吐，也带来一致性问题

下单要改 DB 库存；但用户看到的库存来自 Redis。改 DB 和改缓存的先后顺序决定了「脏数据窗口」：V1 先删缓存，读请求会在窗口期把 DB 旧值回填；V2 反过来，脏窗口几乎消失；V3 用延迟双删补上 V1 的洞；V4 再加 MQ 兜底，连删除失败都覆盖。

观察实验：V1 下单后立刻点「同时查询两个来源」，偶尔能看到缓存值比 DB 值旧（脏数据）；V2~V4 下单后缓存值会保持一致或短暂旧值后追平。
