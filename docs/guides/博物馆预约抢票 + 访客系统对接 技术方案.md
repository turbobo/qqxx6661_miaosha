# 博物馆预约抢票 + 访客系统对接 技术方案

> 项目背景：已有一套访客预约系统，拟引入博物馆预约购票功能，支持抢票。每天放票 2000 张（可配置），周末有瞬时高峰。抢票成功后自动调访客系统完成预约。

---

## 一、业务目标与约束

### 1.1 核心业务流

```
用户登录（访客系统账号）
  ↓
选日期 + 抢票
  ↓
瞬时高峰：2000 张票 1 分钟内抢完
  ↓
抢到 → 异步调访客系统预约
  ↓
预约成功 → 通知用户（短信/消息）
预约失败 → 自动退款 / 重试 / 告警
```

### 1.2 关键约束

| 约束 | 数值 | 来源 |
|---|---|---|
| 单日放票量 | 2000（可配置） | 业务 |
| 抢购峰值 QPS | ~5000（2000 张 / 30s + 余量） | 瞬时高峰 |
| 接口响应 | < 200ms（抢票主流程） | 用户体验 |
| 数据强一致 | **不超卖、不丢单** | 业务底线 |
| 访客系统对接 | MQ 异步消息 | 接口契约 |
| 单用户每日限购 | 1 张（默认） | 业务规则 |

### 1.3 非目标

- 不做支付（如未来接入，本文方案可平滑扩展）
- 不做选座 / 选场次（仅按日期抢）
- 不做实时库存查询的精确性（允许缓存几秒延迟）

## 三、关键技术决策（来自 miaosha 的实测经验）

### 3.1 为什么不用悲观锁

全 Docker 实测（2026-09-18，33 轮）：悲观锁 QPS 272~1783，P99 最高 2480ms，串行化导致高峰排队 RT 暴涨。2000 张票瞬时高峰余量不足。

### 3.2 为什么不用乐观锁

全 Docker 实测（2026-09-18）：50/200/500 VUs 下业务成功率仅 1.0~1.8%，99% 的请求在 CAS 竞争中失败。高争用场景乐观锁反而最慢，且用户感知极差（绝大多数人看到"抢购失败"）。

### 3.3 为什么不用 CacheV5 "终极方案"

全 Docker 实测（2026-09-18）：QPS 2952~3417 看似很高，但业务成功率仅 3.5%，且延迟双删消息在 30 秒压测窗口内积压 19421 条（delCache 队列消费速率远低于投递速率）。**堆砌所有好技术 ≠ 好方案**。

### 3.4 最终选型：Redis 预扣减 + MQ 异步

**理论吞吐**：全 Docker 实测（2026-09-18）MQ 方案 QPS 7478~12729（50/200/500 VUs），对 2000 张票瞬时高峰有 1.5~2.5 倍余量，接口 Avg 仅 4~39ms。

**关键优势**：
- 抢票接口只做 3 件事（校验 + Redis DECR + 入队），平均 <50ms
- 扣库 / 创建订单 / 调访客系统 全异步，不阻塞用户
- Redis 单 key 原子操作天然防超卖

> ⚠️ **压测同时暴露教学版 MQ 接口的原生缺陷**：前置"是否已购"检查是 check-then-act 非原子操作，50 VUs 时实际成单 67 单 > 50 个 userId，存在并发竞态窗口。因此本方案必须用 Redis Lua 把"限购检查 + 库存检查 + 扣减"三步原子化（见 §4.3），并以 DB 唯一索引 `uk_user_date` 兜底。

### 3.5 关键决策 #1：Redis 库存何时扣？

**决策：接口同步阶段、入 MQ 之前扣**（预扣减），用 Lua 脚本保证"限购检查 + 库存检查 + 减库存"三步原子化。

| 时机 | 优点 | 缺点 | 适合度 |
|---|---|---|---|
| ① **接口同步预扣（采用）** | 立刻挡住重复/超卖，接口<50ms | 失败要回补库存 | ✅ |
| ② 入队后再扣 | 接口更轻 | MQ 堆积时用户已"抢到"但实际没库存 → 超卖 | ❌ |
| ③ 消费者扣 | 接口最简单 | 10000 请求都进队列，消费者扣到 2000 后全失败，浪费 8000 次 DB 写入 | ❌ |
| ④ 仅 DB 扣（悲观锁） | 最安全 | 全 Docker 实测 QPS 272~1783、P99 最高 2480ms，扛不住瞬时高峰 | ❌ |

详细时序与失败处理见 **§五.2**。

### 3.6 关键决策 #2：抢票系统 ↔ 访客系统怎么一致？

**决策：本地事务表（outbox） + 可靠消息最终一致 + 定时补偿**。

| 方案 | 一致性 | 性能 | 复杂度 | 推荐度 |
|---|---|---|---|---|
| ① 2PC（强一致） | 强 | 低 | 高 | ❌ 访客系统通常不支持 |
| ② **可靠消息最终一致（采用）** | 最终 | 高 | 中 | ✅ |
| ③ 最大努力通知 + 对账 | 弱 | 高 | 低 | ⚠️ 兜底用 |

② 即阿里 RocketMQ 事务消息 / eBay Outbox Pattern 的业界标准做法，主流电商"下单-扣券-积分"跨系统一致性均采用此模式。

详细流程与故障应对见 **§八**。

## 四、库存模型（核心差异 #1：按日期分库存）

### 4.1 Redis 库存 Key 设计

```
miaosha:stock:{date}         → 当前可用库存（整数）
miaosha:stock:total:{date}   → 总库存（用于前端进度条）
miaosha:user:grabbed:{date}  → Set，已抢到的 userId 集合（单用户限购）
miaosha:order:{date}:{userId}→ 订单状态（抢票 → 预约中 → 成功/失败）
```

### 4.2 库存初始化

每天 00:00 由定时任务（Xxl-Job / Spring Scheduler）触发：

```java
@Scheduled(cron = "0 0 0 * * ?")
public void initDailyStock() {
    LocalDate tomorrow = LocalDate.now().plusDays(1);
    // 未来 7 天都预放票
    for (int i = 1; i <= 7; i++) {
        LocalDate date = tomorrow.plusDays(i);
        int quota = configService.getQuota(date); // 默认 2000，可配置
        String key = "miaosha:stock:" + date;
        if (Boolean.FALSE.equals(redisTemplate.hasKey(key))) {
            redisTemplate.opsForValue().set(key, quota);
            redisTemplate.opsForValue().set("miaosha:stock:total:" + date, quota);
        }
    }
}
```

**可配置**：运营后台可调某天 quota（特展加放、闭馆日置 0）。

### 4.3 库存扣减（Lua 保证原子性）

```lua
-- KEYS[1] = miaosha:stock:{date}
-- KEYS[2] = miaosha:user:grabbed:{date}
-- ARGV[1] = userId
if redis.call('sismember', KEYS[2], ARGV[1]) == 1 then
    return -1  -- 已抢过
end
local stock = tonumber(redis.call('get', KEYS[1]) or 0)
if stock <= 0 then
    return -2  -- 库存不足
end
redis.call('decr', KEYS[1])
redis.call('sadd', KEYS[2], ARGV[1])
redis.call('expire', KEYS[2], 86400 * 7)  -- 7 天过期
return stock - 1
```

**三个关键**：
1. `sismember` 前置 → 拦截重复抢
2. `decr` 原子 → 防超卖
3. 整体 Lua → 三步原子化，无并发窗口

## 五、抢票主流程（接口层）

### 5.1 接口签名

```
POST /api/v1/tickets/grab
Authorization: Bearer <access_token from 访客系统>
Body: { "visitDate": "2026-08-15" }
```

### 5.2 处理流程

```java
@PostMapping("/grab")
public Result<GrabResponse> grab(@RequestBody GrabRequest req,
                                 @RequestHeader("Authorization") String token) {
    // 1. 校验登录态（调访客系统 / 本地缓存 JWT）
    Long userId = authService.getUserId(token);
    if (userId == null) return Result.error("请先登录");

    // 2. 校验日期合法（今天+1 到 今天+7）
    if (!dateService.isValid(req.getVisitDate())) {
        return Result.error("日期不在开放范围");
    }

    // 3. Redis 预扣减（Lua 脚本）
    int result = stockService.tryDecr(req.getVisitDate(), userId);
    if (result == -1) return Result.error("已抢过，每人每日限购 1 张");
    if (result == -2) return Result.error("票已售罄");

    // 4. 入队（MQ 异步创建订单 + 调访客系统）
    TicketMessage msg = new TicketMessage(
        UUID.randomUUID().toString(),
        userId, req.getVisitDate(), System.currentTimeMillis()
    );
    rabbitTemplate.convertAndSend("ticket.order.exchange",
                                   "ticket.order.create",
                                   msg);

    // 5. 快速返回"抢票受理中"
    return Result.success(new GrabResponse(msg.getMessageId(), "处理中"));
}
```

**接口耗时**：<50ms（只做 Redis + MQ 入队，不碰 DB）。

### 5.3 客户端轮询结果

用户提交后前端轮询 `/api/v1/tickets/status?messageId=xxx`：
- 处理中 → 显示"排队中"
- 预约成功 → 显示二维码 / 票号
- 预约失败 → 显示"退款中"

### 5.4 Redis 预扣减详细时序（关键决策 #1）

**完整时序**：

```
用户请求
   ↓
[接口同步] ── Lua 脚本原子执行：
   │  1. sismember(user)   → 已抢过则 -1
   │  2. get stock         → ≤0 则 -2
   │  3. decr stock        → 库存 -1
   │  4. sadd(user)        → 标记已抢
   ↓
返回 200 "处理中"（此时 Redis 已扣）
   ↓
[异步入 MQ] ── 发 ticket.order.create 消息
   ↓
[消费者] ── 落库 ticket_order（状态=RESERVING）+ outbox_message（PENDING）
   ↓
[outbox 任务] ── 扫 PENDING 消息 → 发访客系统 → 更新为 SENT
   ↓
[监听回执] ── 成功 → SUCCESS；失败 → 重试 / 退款回补库存
```

**"扣了但失败"的三种场景 + 处理**：

| 场景 | 时机 | 处理 |
|---|---|---|
| 接口成功但 MQ 入队失败 | 接口同步阶段 | try-catch 包裹，MQ 失败立即 `incr` 回补库存 + `srem` 移除用户 |
| 消费者处理失败（MQ / DB / 访客系统） | 异步阶段 | 消费者重试 3 次；超次 → 状态 REFUNDING → `incr` 回补 + 短信通知 |
| 整个服务挂了 | 任意 | 定时任务（1 分钟）扫 RESERVING 订单，超 30 分钟未流转 → 自动回补 |

**每日对账（兜底）**：每天凌晨跑一次对账脚本，比对三个数据源：

```
Redis 实际扣减 = quota - stock_current
DB 订单数      = COUNT(*) WHERE status IN (RESERVING, SUCCESS)
访客系统预约数 = COUNT(success 回执)

三者必须：Redis 扣减 == DB 订单数
        DB 订单数 >= 访客预约数（允许在途的 RESERVING）
```

不一致 → 钉钉告警 + 自动生成差异报表。

## 六、订单消费者（异步核心）

### 6.1 消息处理流程（写入本地事务表，不直接发 MQ）

**核心改动**：消费者不再直接 `rabbitTemplate.send`，而是**写本地 outbox_message 表**，由独立任务异步发送（详见 §八.1）。这样"订单落库"和"消息待发"在一个 DB 事务里，保证"订单在 → 消息一定在"。

```java
@RabbitListener(queues = "ticket.order.queue")
@Transactional
public void handleOrder(TicketMessage msg) {
    // 1. 幂等检查（同一 messageId 只处理一次）
    if (orderRepo.existsById(msg.getMessageId())) return;

    // 2. 创建订单（状态=预约中）
    TicketOrder order = new TicketOrder();
    order.setMessageId(msg.getMessageId());
    order.setUserId(msg.getUserId());
    order.setVisitDate(msg.getVisitDate());
    order.setStatus(OrderStatus.RESERVING);
    orderRepo.save(order);

    // 3. 写入本地事务表（outbox），状态=PENDING
    //    与订单在同一个 DB 事务，原子性保证
    OutboxMessage outbox = new OutboxMessage();
    outbox.setMessageId(msg.getMessageId());
    outbox.setExchange("visitor.reserve.exchange");
    outbox.setRoutingKey("visitor.reserve.create");
    outbox.setPayload(buildReservePayload(msg));
    outbox.setStatus(OutboxStatus.PENDING);
    outboxRepo.save(outbox);
}
```

> ⚠️ **关键**：这里没有 `rabbitTemplate.send`。发消息由 §八.1 的 Outbox 异步发送任务负责。

### 6.2 监听访客系统回执

```java
@RabbitListener(queues = "ticket.reserve.reply.queue")
@Transactional
public void handleReply(VisitorReserveReply reply) {
    TicketOrder order = orderRepo.findById(reply.getMessageId())
                                  .orElseThrow();

    // 幂等保护：已处理过的回执直接忽略（防止 MQ 重试导致状态回退）
    if (order.getStatus() != OrderStatus.RESERVING) {
        log.warn("已处理过，忽略回执: {} 当前状态: {}",
                 reply.getMessageId(), order.getStatus());
        return;
    }

    if (reply.isSuccess()) {
        order.setStatus(OrderStatus.SUCCESS);
        order.setVisitorId(reply.getVisitorId());  // 访客系统单号
        // 更新 outbox 状态为 REPLIED
        outboxRepo.markReplied(reply.getMessageId());
        // 发送短信/消息通知用户
        notifyService.success(order);
    } else {
        // 预约失败：重试或退款
        if (order.getRetryCount() < 3) {
            order.setRetryCount(order.getRetryCount() + 1);
            orderRepo.save(order);
            // 把 outbox 状态改回 PENDING，让 Outbox 任务重新发送
            outboxRepo.resetToPending(reply.getMessageId());
        } else {
            order.setStatus(OrderStatus.REFUNDING);
            stockService.incr(order.getVisitDate());  // 库存回补
            notifyService.refund(order);
            alertService.alert("预约失败超 3 次", order);
        }
    }
    orderRepo.save(order);
}
```

## 七、消息契约（与访客系统的接口协议）

### 7.1 我方发送：预约请求

**Exchange**：`visitor.reserve.exchange`（topic）  
**RoutingKey**：`visitor.reserve.create`  
**Queue**：`visitor.reserve.queue`（访客系统监听）

```json
{
  "messageId": "uuid",
  "userId": 12345,              // 访客系统账号 ID
  "visitDate": "2026-08-15",
  "externalOrderNo": "MUSEUM_TICKET_xxx",
  "ticketType": "ADULT",
  "timestamp": 1786000000000
}
```

### 7.2 访客系统回执：预约结果

**Exchange**：`ticket.reserve.reply.exchange`  
**RoutingKey**：`ticket.reserve.reply`  
**Queue**：`ticket.reserve.reply.queue`（我方监听）

```json
{
  "messageId": "uuid",          // 与我方发送的一致
  "success": true,
  "visitorId": "V20260815001",  // 访客系统单号
  "failReason": null,
  "timestamp": 1786000050000
}
```

### 7.3 可靠性保障

| 环节 | 机制 |
|---|---|
| 消息不丢 | RabbitMQ 持久化队列 + 持久化消息 |
| 消息不重 | 消费端 messageId 幂等检查 |
| 我方发送失败 | 开启 confirm + return 回调，重试 3 次 |
| 访客系统发送失败 | 开启 confirm + return 回调 |
| 回执丢失 | 我方定时任务扫描 RESERVING 状态订单，超 5 分钟重发请求 |
| 双活 | 我方 + 访客系统都各自有死信队列兜底 |

## 八、分布式一致性（关键决策 #2：抢票系统 ↔ 访客系统）

### 8.1 本地事务表（Outbox Pattern）

**核心思路**：把"订单落库"和"发预约消息"绑定成一个本地 DB 事务，再配合定时补偿 + 回执确认，达到最终一致。

#### 表结构

```sql
CREATE TABLE outbox_message (
    message_id VARCHAR(64) PRIMARY KEY,
    exchange VARCHAR(64) NOT NULL,
    routing_key VARCHAR(64) NOT NULL,
    payload TEXT NOT NULL,
    status VARCHAR(20) NOT NULL,    -- PENDING / SENT / REPLIED / FAILED
    retry_count INT DEFAULT 0,
    created_at DATETIME NOT NULL,
    updated_at DATETIME NOT NULL,
    INDEX idx_status_retry (status, retry_count, created_at)
);
```

#### 4 步闭环流程

```
┌──────────────── 抢票系统 ────────────────┐
│                                          │
│  Step 1: 本地事务（MySQL）                │
│  ─────────────────────────               │
│  BEGIN TRANSACTION                       │
│    INSERT ticket_order (RESERVING)       │
│    INSERT outbox_message (PENDING)       │
│  COMMIT                                  │
│                                          │
│  Step 2: 异步发送（RabbitMQ）             │
│  ─────────────────────────               │
│  读 outbox_message 未发送的 →            │
│  发到 visitor.reserve.exchange →         │
│  更新 outbox_message = SENT              │
│                                          │
│  Step 3: 监听回执                         │
│  ─────────────────────────               │
│  收到 visitor.reserve.reply →            │
│  UPDATE ticket_order = SUCCESS           │
│  UPDATE outbox_message = REPLIED         │
└──────────────────────────────────────────┘
                ↕ MQ
┌──────────────── 访客系统 ────────────────┐
│  消费 visitor.reserve.queue              │
│  创建访客预约                             │
│  回执 visitor.reserve.reply              │
└──────────────────────────────────────────┘
```

#### Outbox 异步发送任务

```java
@Scheduled(fixedRate = 5000)  // 每 5 秒
public void sendPendingOutbox() {
    // 拉取 PENDING 状态消息（最多 100 条）
    List<OutboxMessage> pending = outboxRepo.findPending(100);
    for (OutboxMessage msg : pending) {
        try {
            rabbitTemplate.convertAndSend(
                msg.getExchange(),
                msg.getRoutingKey(),
                msg.getPayload(),
                m -> {
                    m.getMessageProperties().setMessageId(msg.getMessageId());
                    return m;
                }
            );
            msg.setStatus(OutboxStatus.SENT);
            msg.setUpdatedAt(new Date());
            outboxRepo.save(msg);
        } catch (Exception e) {
            log.warn("发送失败，下次重试: {}", msg.getMessageId());
        }
    }
}
```

### 8.2 定时补偿任务（防回执丢失）

```java
@Scheduled(fixedRate = 60000)  // 每分钟
public void compensateReserving() {
    // 扫 RESERVING 超 5 分钟 且 outbox 状态=SENT（消息已发但没回执）
    List<TicketOrder> orphans = orderRepo.findReservingOlderThan(5, TimeUnit.MINUTES);
    for (TicketOrder order : orphans) {
        if (order.getRetryCount() < 3) {
            // 重发：把 outbox 状态改回 PENDING
            outboxRepo.resetToPending(order.getMessageId());
            order.setRetryCount(order.getRetryCount() + 1);
        } else {
            // 重试 3 次仍无回执 → 退款
            order.setStatus(OrderStatus.REFUNDING);
            stockService.incr(order.getVisitDate());
            notifyService.refund(order);
            alertService.alert("预约失败超 3 次", order);
        }
        orderRepo.save(order);
    }
}
```

### 8.3 回执幂等 + 防重发

访客系统可能重发回执（MQ 重试），我方必须幂等处理：

```java
@RabbitListener(queues = "ticket.reserve.reply.queue")
public void handleReply(VisitorReserveReply reply) {
    TicketOrder order = orderRepo.findById(reply.getMessageId())
                                  .orElseThrow();
    // 幂等保护：已处理过的回执直接忽略（防止 MQ 重试导致状态回退）
    if (order.getStatus() != OrderStatus.RESERVING) {
        log.warn("已处理过，忽略回执: {}", reply.getMessageId());
        return;
    }
    // ... 正常处理（详见 §6.2）
}
```

### 8.4 四种故障场景的应对

| 故障 | 影响 | 自愈机制 |
|---|---|---|
| 我方发预约消息失败 | 访客系统没收到 | outbox 任务 5 秒重试 |
| 访客系统处理慢 | 用户等待 | RESERVING 状态最长 5 分钟，超时重发 |
| 访客系统回执丢失 | 我方不知道结果 | 补偿任务重发预约请求 |
| 访客系统彻底挂了 | 无法完成预约 | 重试 3 次后自动退款 + 短信通知 |
| 我方消费者挂掉 | MQ 消息堆积 | RabbitMQ 自动重平衡 + 死信队列兜底 |

### 8.5 极端情况：访客系统持续不可用（降级预案）

如果访客系统故障 > 1 小时，触发降级：

1. 抢票接口正常接（Redis 扣减不变）
2. 所有订单保持 RESERVING 状态，**不退款**
3. 短信通知用户"预约确认中，预计 X 小时内完成"
4. 访客系统恢复后，补偿任务自动追平

**原则**：宁可延迟，不要退款（退款意味着票作废，用户体验极差）。

### 8.6 一张图看清两套系统的"边界 + 一致性"

```
用户 → [API] → [Redis 扣减] → [MQ] → [DB 落库 + outbox] → [MQ] → 访客系统 → [回执]
          ↑ 同步区 ↑              ↑ 异步区（最终一致）        ↑ 第三方

责任边界：
- Redis 扣减成功 = 我方已承诺给用户一张票（不可撤销，除非明确失败）
- 访客系统回执成功 = 整个流程完结
- 中间任意阶段失败 = 自动重试 + 补偿 + 兜底退款
```

## 十、防超卖、防丢单、防刷（三个"防"）

### 10.1 防超卖（库存准确）

- **主防线**：Redis Lua 脚本原子扣减（第四节）
- **兜底**：DB 订单数 ≤ quota 校验（定时任务对账）
- **补偿**：每日凌晨跑对账脚本，比对 `ticket_order.count(SUCCESS)` 与 `quota - redis.stock`，不一致告警

### 10.2 防丢单（订单完整）

- **主防线**：MQ 消息持久化 + 消费 ACK
- **兜底**：订单表 RESERVING 状态订单，超 5 分钟定时任务扫一遍，重发预约请求
- **告警**：RESERVING 订单 > 30 分钟未流转，触发告警

### 10.3 防刷（风控）

- **接口层**：单 userId QPS 限 5、单 IP QPS 限 20（Sentinel）
- **业务层**：Redis 已抢集合（单用户限购）
- **网关层**：验证码（瞬时 QPS > 1000 时启用）、设备指纹
- **监控层**：异常用户（1 分钟抢 100+ 次）自动拉黑

## 十七、方案选型结论与压测验证（2026-09 更新）

### 17.1 选型结论（一句话）

> 限流防刷在前（令牌桶 + 验签），Redis Lua 预扣挡超卖，MQ 异步扛峰值，Outbox 事务消息保跨系统最终一致，熔断 + 补偿 + 对账兜底——淘宝秒杀（预扣 + MQ）与电商事务消息（Outbox）两个主流模式的组合。

### 17.4 微信生态适配（增量建议）

1. **通知通道**：预约结果优先用公众号模板消息/服务通知，前端轮询（§5.3）只是辅助，用户不会盯着页面等结果。
2. **分时段预约（建议补）**：国博/故宫实践证明分时段可削峰 70%+。2000 张票按 9:00-17:00 分 8 时段放，单时段峰值从 ~5000 QPS 降至 ~1000，全链路压力骤减。库存 Key 由 `miaosha:stock:{date}` 细化为 `miaosha:stock:{date}:{slot}`，其余设计不变。

### 17.5 教学版接口升级点（压测暴露的真实缺陷）

1. **s5_mq 去重竞态**：前置"是否已购"检查非原子（50 VUs 时 sale=67 > 50 个 userId）。生产实现必须用 Redis Lua 原子化（§4.3 已设计）+ DB 唯一索引 `uk_user_date` 兜底。
2. **s4_cache_v5 延迟双删积压**：30 秒窗口 delCache 积压 19421 条，异步删除的延迟窗口放大后即缓存与 DB 不一致的风险面——生产上删除消息要独立消费组 + 限速 + 积压告警。
