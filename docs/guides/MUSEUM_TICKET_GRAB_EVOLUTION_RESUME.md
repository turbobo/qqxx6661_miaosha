# 博物馆微信公众号抢票系统逐步演进方案（简历项目描述版）

## 1. 项目背景

面向博物馆微信公众号预约场景，节假日、寒暑假和周末会出现大量用户在开票瞬间集中抢票。系统需要在高并发下保证库存准确、用户体验稳定，并具备防刷、防重复预约、异步削峰和结果可追踪能力。
你说那啥都有你
本项目围绕“微信公众号抢票”核心链路，从同步数据库扣库存逐步演进为基于 Redis、Lua、MQ、幂等落单和异步结果查询的高并发抢票方案。

## 2. 技术栈

- 后端：Spring Boot、Spring MVC、MyBatis
- 缓存与并发控制：Redis、Redis Lua、分布式锁、分布式限流
- 消息队列：RabbitMQ
- 数据库：MySQL
- 微信生态：微信公众号 OAuth、openId / unionId 用户身份体系
- 稳定性：幂等控制、重试补偿、死信队列、库存对账、接口监控

## 3. 业务目标

- 支持用户在微信公众号内选择日期、场次并提交抢票请求。
- 支持节假日、周末等高峰期开票瞬时流量。
- 保证同一用户、同一日期、同一场次不能重复预约。
- 保证库存不超卖、不少卖。
- 抢票接口快速返回，用户可查询排队、成功、失败等明确状态。
- 对异常用户、脚本请求、重复提交进行限流和拦截。

## 4. 演进过程

### 阶段一：基础同步下单版本

最初版本采用传统同步接口处理抢票请求。

流程：

```text
用户提交抢票请求
  ↓
Controller 参数校验
  ↓
查询数据库库存
  ↓
扣减数据库库存
  ↓
创建订单
  ↓
返回抢票结果
```

主要问题：

- 所有请求直接打到数据库，高峰期数据库压力大。
- 并发扣库存容易出现超卖风险。
- 接口响应时间受数据库锁、订单创建、外部调用影响。
- 用户重复点击可能造成重复下单。

简历表达：

- 负责实现微信公众号票务预约基础链路，完成票务查询、抢票下单、订单生成和结果返回等核心功能。
- 在基础版本中识别出高并发下数据库库存竞争、重复下单和接口响应慢等瓶颈，为后续架构演进提供优化方向。

### 阶段二：数据库锁保证库存正确性

为解决并发超卖问题，引入数据库悲观锁或乐观锁。

悲观锁方案：

```text
select ... for update 锁定库存行
  ↓
判断剩余库存
  ↓
扣减库存
  ↓
创建订单
  ↓
提交事务释放锁
```

乐观锁方案：

```text
查询库存和 version
  ↓
update stock set remaining = remaining - 1, version = version + 1
where id = ? and version = ? and remaining > 0
```

优化效果：

- 解决高并发扣库存超卖问题。
- 乐观锁减少数据库行锁等待，提高并发处理能力。
- 通过重试机制处理版本冲突。

主要难点：

- 悲观锁能保证强一致，但高并发下锁等待严重。
- 乐观锁吞吐更高，但热点库存行冲突频繁，需要控制重试次数和退避策略。
- 库存扣减和订单创建必须在同一事务内保证一致性。

简历表达：

- 针对抢票库存热点竞争问题，设计并实现悲观锁与乐观锁两套扣库存方案，通过版本号 CAS 更新解决并发超卖问题。
- 对乐观锁冲突引入有限重试和随机退避，降低热点库存行竞争下的失败率和数据库压力。

### 阶段三：前置校验与防刷限流

数据库锁只能保护库存正确性，不能保护系统不被无效流量打垮。因此将低成本校验前置。

校验顺序调整为：

```text
参数校验
  ↓
活动状态校验
  ↓
微信身份校验
  ↓
用户级限流
  ↓
接口级限流
  ↓
抢票 hash 校验
  ↓
抢票时间校验
  ↓
库存校验
  ↓
下单处理
```

关键能力：

- 使用 openId / unionId 识别微信用户身份。
- 下单前生成短期 verifyHash，避免脚本直接刷抢票接口。
- 对用户、IP、接口、票种维度进行限流。
- 对异常频率用户进行拦截或降级。

主要难点：

- 限流粒度需要兼顾公平性和系统吞吐。
- 抢票 hash 需要短期有效、防重放，并绑定用户和场次。
- 单机限流无法支撑多实例部署，需要演进到 Redis 分布式限流。

简历表达：

- 将抢票链路中的参数校验、活动状态、用户限流、接口限流和 hash 校验前置，用低成本操作拦截无效请求，降低数据库访问压力。
- 基于 Redis 实现用户级、接口级、票种级分布式限流，解决多节点部署下单机限流不准确的问题。

### 阶段四：Redis 原子预扣库存

为避免抢票流量直接进入数据库，将库存热点从 MySQL 前移到 Redis。

核心链路：

```text
抢票请求
  ↓
前置校验
  ↓
Redis Lua 判断是否已购
  ↓
Redis Lua 判断库存是否充足
  ↓
Redis Lua 预扣库存
  ↓
标记用户已抢占
  ↓
返回排队状态
```

Redis Key 设计：

```text
ticket:stock:{date}:{sessionId}                  剩余库存
ticket:purchased:{date}:{sessionId}:{userId}     用户是否已抢占
ticket:request:{requestId}                       请求状态
ticket:user:request:{date}:{sessionId}:{userId}  用户请求编号
```

Lua 脚本需要原子完成：

```text
1. 判断用户是否重复抢票
2. 判断库存是否大于 0
3. 库存扣减 1
4. 写入用户抢占标记
5. 写入请求初始状态
```

优化效果：

- 大量无效请求在 Redis 层被快速拦截。
- 数据库只处理 Redis 预扣成功的有效请求。
- 库存扣减由 Lua 脚本保证原子性，避免 Redis 层并发超卖。

主要难点：

- Redis 预扣成功后，如果后续 MQ 或数据库失败，需要回滚库存和用户占位。
- Redis 库存与 MySQL 最终库存需要定时对账。
- Redis key 需要设置合理过期时间，避免长期脏数据。

简历表达：

- 将库存热点前移到 Redis，基于 Lua 脚本实现库存判断、重复预约判断、库存预扣和用户占位的原子操作，将数据库压力从全量请求降低到有效请求。
- 设计 Redis 预扣失败回滚和库存对账机制，解决缓存库存与数据库库存最终一致性问题。

### 阶段五：MQ 异步削峰落单

Redis 预扣成功后，不再同步创建订单，而是投递 MQ，由消费者异步落库。

抢票接口链路：

```text
前置校验
  ↓
Redis 原子预扣库存
  ↓
生成 requestId
  ↓
写入 QUEUED 状态
  ↓
发送 RabbitMQ
  ↓
立即返回 requestId
```

消费者链路：

```text
消费抢票消息
  ↓
requestId 幂等检查
  ↓
userId + date + sessionId 幂等检查
  ↓
创建订单
  ↓
生成票码
  ↓
更新数据库库存 / 销量
  ↓
写入抢票结果 SUCCESS
```

优化效果：

- 抢票接口从同步落单变为快速提交，响应时间显著降低。
- MQ 承担削峰填谷能力，数据库按消费者能力平滑处理订单。
- 通过结果查询接口补齐用户体验。

主要难点：

- MQ 消息可能重复投递，消费者必须幂等。
- MQ 发送失败时，需要回滚 Redis 预扣库存。
- 消费失败后需要重试、死信队列和人工补偿能力。
- 用户成功抢占 Redis 库存不代表最终订单一定成功，需要明确状态流转。

简历表达：

- 将抢票接口改造为 Redis 预扣库存 + RabbitMQ 异步落单模式，实现请求削峰和快速响应，避免数据库在开票瞬间被流量打穿。
- 设计消费者幂等机制，通过 requestId、userId + date + sessionId 唯一约束防止重复消费和重复下单。
- 设计 MQ 失败回滚、消费重试、死信队列和补偿任务，提升抢票链路的容错能力。

### 阶段六：异步结果查询与用户体验优化

异步抢票后，用户不能立即拿到最终订单，需要提供明确的结果查询能力。

状态模型：

```text
QUEUED      排队中
PROCESSING  处理中
SUCCESS     抢票成功
FAILED      抢票失败
SOLD_OUT    已售罄
DUPLICATE   重复预约
TIMEOUT     超时
```

查询链路：

```text
前端轮询 requestId
  ↓
优先查询 Redis 结果缓存
  ↓
命中则返回状态
  ↓
未命中再兜底查询数据库
```

优化效果：

- 避免前端频繁轮询数据库。
- 用户能看到“排队中、成功、失败、售罄”等明确状态。
- 可通过状态缓存支撑高并发结果查询。

主要难点：

- 前端轮询本身也可能形成流量峰值，需要对查询接口限流。
- 结果状态需要和 MQ 消费状态保持一致。
- 超时请求需要后台任务识别并更新状态。

简历表达：

- 设计异步抢票结果查询机制，将请求状态写入 Redis，前端基于 requestId 轮询查询排队、成功、失败、售罄等状态，降低用户等待不确定性。
- 对结果查询接口增加缓存和频控，避免抢票成功后的轮询流量反向冲击数据库。

### 阶段七：一致性、补偿与监控治理

抢票链路涉及 Redis、MQ、MySQL，多组件之间必须处理最终一致性。

一致性保障：

- Redis 预扣成功但 MQ 发送失败：回滚 Redis 库存和用户占位。
- MQ 消费失败：自动重试，超过阈值进入死信队列。
- DB 创建订单失败：回滚 Redis 库存，更新请求状态为 FAILED。
- Redis 与 DB 不一致：定时任务以成功订单数为准进行库存对账。

监控指标：

- 抢票接口 QPS
- 接口平均耗时、P95、P99
- Redis 预扣成功数、失败数
- 限流拦截数
- 重复预约拦截数
- MQ 堆积量
- MQ 消费成功率
- 订单创建成功率
- 库存对账异常数

简历表达：

- 建立 Redis、MQ、MySQL 多组件最终一致性方案，覆盖 MQ 发送失败、消费失败、数据库落单失败和库存不一致等异常场景。
- 接入链路监控和关键业务指标统计，对抢票 QPS、限流拦截、MQ 堆积、订单成功率和库存对账异常进行观测，提升高峰期问题定位效率。

## 5. 项目重点

### 重点一：高并发库存扣减

抢票场景的核心是库存热点竞争。项目从数据库悲观锁、乐观锁逐步演进到 Redis Lua 原子预扣库存，解决了高并发下库存超卖和数据库热点行竞争问题。

### 重点二：异步削峰

通过 RabbitMQ 将抢票请求和订单创建解耦，抢票接口只负责校验、预扣和排队，数据库按消费者能力平滑处理订单，提升系统高峰期稳定性。

### 重点三：幂等与防重复预约

在 Redis 层通过用户占位防止重复抢占，在数据库层通过唯一索引防止重复落单，在 MQ 消费层通过 requestId 防止重复消费，实现多层幂等保护。

### 重点四：最终一致性

Redis 预扣、MQ 异步、MySQL 落单之间不是强事务，需要通过失败回滚、重试、死信队列、补偿任务和库存对账保证最终一致。

### 重点五：防刷与限流

通过微信 openId、verifyHash、用户级限流、接口级限流、票种级限流等手段拦截脚本刷票和异常流量，保护核心下单链路。

## 6. 项目难点

- **库存不超卖**：高并发下库存扣减必须原子化，不能依赖普通查询再更新。
- **一人一票**：需要同时在 Redis、MQ 消费者和数据库唯一索引层面防重复。
- **高峰削峰**：开票瞬间流量远超数据库承载能力，需要 Redis + MQ 分层削峰。
- **失败回滚**：Redis 预扣成功后，MQ 或 DB 任一环节失败都要正确释放库存。
- **结果可感知**：异步链路下，用户无法同步拿到结果，需要设计清晰的状态查询机制。
- **数据一致性**：Redis 库存、DB 库存、成功订单数需要定时对账和修正。
- **防刷公平性**：既要拦截异常高频请求，又不能误伤正常用户。

## 7. 简历项目描述示例

### 版本一：完整项目描述

博物馆微信公众号高并发抢票系统：面向节假日和周末开票瞬时高峰，设计并实现基于 Redis、Lua、RabbitMQ 和 MySQL 的异步抢票链路。系统通过微信 openId 身份校验、短期 verifyHash、防重复预约、分布式限流、Redis 原子预扣库存、MQ 异步落单和 Redis 结果查询，实现抢票请求快速响应、库存不超卖、一人一票和高峰流量削峰。针对 Redis 预扣成功但 MQ/DB 失败等异常场景，设计库存回滚、消费重试、死信队列、补偿任务和库存对账机制，保障多组件链路最终一致性。

### 版本二：简历项目职责

- 负责博物馆微信公众号抢票核心链路设计与实现，支持用户按日期和场次进行在线预约抢票。
- 基于 Redis Lua 实现库存判断、重复预约判断、库存预扣和用户占位的原子操作，解决高并发下库存超卖问题。
- 引入 RabbitMQ 异步削峰，将抢票接口从同步落单改造为“预扣库存 + 消息排队 + 异步落单”，降低数据库瞬时写入压力。
- 设计 requestId、userId + date + sessionId、数据库唯一索引等多层幂等机制，防止重复提交、重复消费和重复下单。
- 设计异步抢票结果查询模型，支持 QUEUED、PROCESSING、SUCCESS、FAILED、SOLD_OUT、DUPLICATE、TIMEOUT 等状态流转。
- 建立失败回滚、消息重试、死信队列、补偿任务和库存对账机制，保障 Redis、MQ、MySQL 之间的最终一致性。
- 对抢票接口增加用户级、接口级、票种级分布式限流，并结合微信身份和 verifyHash 校验提升防刷能力。

### 版本三：项目亮点写法

- **高并发库存扣减**：使用 Redis Lua 将库存校验、库存扣减和用户占位合并为原子操作，避免并发抢票下库存超卖。
- **异步削峰落单**：基于 RabbitMQ 解耦抢票请求与订单创建，抢票接口只做校验和排队，数据库按消费能力平滑处理订单。
- **多层幂等控制**：通过 Redis 用户占位、requestId 消费幂等和 MySQL 唯一索引，防止重复预约和重复落单。
- **最终一致性保障**：针对 MQ 发送失败、消费失败、DB 落单失败设计回滚、重试、死信队列和库存对账机制。
- **防刷与限流**：结合微信 openId、短期 verifyHash、Redis 分布式限流和异常用户拦截，提升抢票公平性和系统稳定性。

## 8. 面试讲解思路

可以按照下面顺序讲：

```text
1. 为什么普通同步下单扛不住？
2. 如何用数据库锁先保证不超卖？
3. 为什么数据库锁仍然有性能瓶颈？
4. 为什么把库存前移到 Redis？
5. Redis 预扣为什么必须用 Lua？
6. 为什么需要 MQ 异步落单？
7. MQ 重复消费和失败如何处理？
8. Redis、MQ、DB 如何保证最终一致？
9. 用户怎么知道最终抢票结果？
10. 节假日高峰怎么限流和降级？
```

重点突出：

- 不是一开始就上复杂架构，而是从问题驱动逐步演进。
- 每一次优化都解决一个明确瓶颈。
- 不只关注性能，也关注正确性、幂等、一致性和用户体验。
