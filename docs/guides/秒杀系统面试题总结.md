## 项目一句话介绍

基于 Spring Boot + Redis + RabbitMQ + MySQL 的秒杀抢购系统，用 7 个演进阶段（无锁 → 锁策略 → 缓存一致性 → 异步削峰 → 接口防护 → 工程化）完整模拟了秒杀系统从「卖不对」到「卖得稳」的演进过程，并用 40 轮 JMeter 压测验证每个方案的优劣。

### 核心数据速查（面试时甩数据）

| 方案 | HTTP QPS | 业务成功率 | 平均 RT |
|---|---|---|---|
| 无锁（反面） | 3158 | **0.6%~1.1%**（超卖） | 15ms |
| 乐观锁 | 4146 | **1.1%~1.7%**（CAS 冲突） | 12ms |
| 悲观锁 | 213~340 | **94%~100%** | 148~898ms |
| 缓存 V1~V4 | 269~319 | 98%~100% | ~500ms |
| MQ 异步 | **3944** | 取决于消费速率 | **43ms** |

## 一、系统架构设计

### Q1：请介绍你的秒杀系统整体架构

**答法**：三层多模块 Maven 工程 + 三大中间件。

- **模块划分**：`miaosha-dao`（数据访问）、`miaosha-service`（业务逻辑）、`miaosha-web`（控制器 + 前端），单向依赖 web → service → dao，禁止反向依赖
- **中间件**：MySQL 8（库存/订单持久化）、Redis 6（缓存 + 分布式锁 + 限流 + 幂等标记）、RabbitMQ 3（异步削峰 + 延迟双删兜底）
- **核心链路**：前端 → SeckillController → 校验（限流/验签/幂等）→ 扣库存（锁策略）→ 写订单 → 异步通知

### Q2：秒杀系统从 0 到 1 怎么演进？每一步解决什么问题？

本项目最核心的叙事线，按「问题 → 方案 → 新问题」链式回答：

| 阶段 | 解决的问题 | 方案 | 引入的新问题 |
|---|---|---|---|
| 0 无锁 | 基线（反面教材） | 查库存→sale+1→插订单 | 并发覆盖，业务成功率 5.6% |
| 1 锁策略 | 并发丢数据 | 悲观锁 FOR UPDATE / 乐观锁 version | 吞吐受限 / 冲突率高 |
| 2 缓存 | DB 成瓶颈 | Redis 挡在读路径前 | **缓存一致性** |
| 3 双写策略 | 缓存脏数据 | V1~V4：延迟双删、MQ 兜底 | 工程复杂度 |
| 4 MQ 异步 | 同步扣库慢 | 接口只入队，消费者落库 | 端到端延迟、排队 |
| 5 接口防护 | 脚本刷单 | 验签 hash + 限频 | 用户多一步 |
| 6 工程化 | 集群/可靠性 | 分布式锁、幂等、分布式限流、熔断 | — |

**面试加分句**：架构演进不是「越新越好」，而是「每代解决上一代的特定痛点」，项目里 V5「技术堆砌版」QPS 只有 7，证明堆砌好技术不等于好架构。

### Q3：乐观锁和悲观锁怎么选？（必考题）

**结合实测回答**：
- **悲观锁**（`SELECT ... FOR UPDATE`）：事务内锁行，排队串行化。实测 50~500 VUs 下 QPS 稳定 328~340、业务成功率 94%~100%。**适合高争用 + 强一致场景**
- **乐观锁**（`UPDATE ... WHERE version=?`）：靠版本号 CAS。实测 HTTP QPS 高达 4146，但**业务成功率仅 1.1%**——50 个线程同时读同一个 version，49 个冲突回滚，请求白跑
- **反直觉结论**：高争用下乐观锁反而比悲观锁慢（业务 QPS 13 vs 328）。乐观锁适合「争用少、冲突概率低」的场景，比如单用户维度（userId+date 唯一）的防重

### Q4：高并发下如何防止超卖？（分层回答，展示知识广度）

**从单机到集群依次加码**（项目全部实现过）：
1. **原子 SQL**：`UPDATE stock SET sale = sale + 1 WHERE id = ? AND sale < count`（影响行数=0 即卖完）
2. **悲观锁**：行锁串行化，最稳但吞吐低
3. **乐观锁**：version 字段 CAS，高争用下冲突率高
4. **Redis 预扣减**：库存放 Redis，Lua 脚本原子校验+扣减
5. **分布式锁**（Redisson）：多实例部署时锁的互斥依然成立
6. **MQ 异步**：扣减放到消费者串行处理，DB 压力可控

### Q5：如何防止脚本刷单 / 恶意请求？

项目用了三道防线：
1. **接口隐藏 + 验签**（stage3）：下单前必须先调 `verify-hash` 领取 MD5 凭证（服务端校验时段/用户/商品后签发，存 Redis 3600 秒），下单接口必须携带合法 hash 才放行——脚本拿不到 hash 就无从刷起
2. **限频**：60 秒窗口内单用户访问超 3 次即封禁（Redis 计数）
3. **限流**：Guava 令牌桶（单机 10 令牌/秒）→ Redis + Lua 分布式令牌桶（集群共享配额，解决「每台各放 10 个」的失效问题）

### Q6：分布式锁怎么设计的？有什么坑？

项目用 **Redisson**（替换自研 SETNX 锁），关键设计：
- **Watchdog 自动续期**：`leaseTime <= 0` 时不传租期，默认 30s 锁、每 10s 续一次，业务超时不丢锁
- **可重入**：RLock 同一线程可多次加锁不死锁
- **安全释放**：`unlock` 前用 `isHeldByCurrentThread()` 校验，**防止误释放别人的锁**；锁内业务 try-finally 释放
- **坑**：自研 SETNX 锁无续期机制，业务执行超过锁过期时间会「锁被别人抢走」，导致并发扣减

### Q7：接口幂等怎么实现？

三层防护：
1. **requestId + Redis SETNX**：前端生成 UUID，SETNX 原子标记（5 分钟有效），重复 requestId 在进入业务前就被拦下
2. **业务终态检查**：用户已购缓存（USER_HAS_ORDER），重复下单直接返回「你已经抢购过了」
3. **DB 唯一索引兜底**：`uk_user_date`（userId+日期）唯一索引，即使前两层失效数据库也拒绝重复写入
- **细节加分**：下单失败时 `removeIdempotentMark(requestId)` 释放标记允许重试，成功则保留拒绝重复提交

### Q8：熔断降级怎么做的？

用 **Resilience4j**（1.7.1，兼容 Java 8 + Spring Boot 2.2.5），对 DB/Redis/MQ 三个依赖分别建熔断器：
- 慢调用率 60% 或错误率过高 → 熔断 60 秒 → 熔断打开时直接走降级逻辑（返回「系统繁忙，已触发熔断降级」）
- 提供 `/circuit-breaker-status` 监控接口查看状态（CLOSED/OPEN/HALF_OPEN）
- **目的**：DB 抖动时快速失败，防止故障扩散拖垮整条链路

### Q9：压测怎么做？HTTP QPS 和业务 QPS 有什么区别？

- **方法**：JMeter 参数化（50/200/500/1000 VUs × 10 策略 = 40 场景），场景隔离（每个方案独立 sid、库存预置 10000），shell 脚本编排（备份历史结果 → 重置库存 → 逐场景压测 → 解析生成报告）
- **关键认知**：HTTP QPS ≠ 业务 QPS。无锁方案 HTTP QPS 3158 看起来最快，但**业务成功率仅 0.6%~1.1%**——请求都「成功」了但订单没落库。面试官问「怎么评估压测结果」时，必须说要看**业务订单数**而非 HTTP 成功率

## 二、MQ 相关

### Q1：为什么秒杀系统要用 MQ？

**核心：削峰填谷 + 解耦 + 异步化**。
- 秒杀的流量曲线是「瞬间尖峰」：开抢 1 秒内几十万请求涌入
- 项目实测：同步扣库（悲观锁）QPS 仅 213~340；改成「接口只入队」后 **QPS 3944（11.6 倍）、平均 RT 43ms（1/11）**
- MQ 把「尖峰」缓冲成消费者可以慢慢消费的「平缓流量」，保护 DB

### Q2：MQ 异步下单的完整流程？（必考题）

```
前端 → 接口（3 步，不碰 DB）
  ① 查缓存：用户是否已抢购（Redis Set 去重，防单用户重复）
  ② 查缓存：库存是否还有
  ③ 发送消息到 orderQueue（sid + userId）
  → 毫秒级返回「提交成功」
消费者（后台）
  ④ 查 user 表校验用户合法性
  ⑤ 乐观锁扣库存（UPDATE ... WHERE version=?）
  ⑥ 写订单记录 + 异步落库
  ⑦ 写入 USER_HAS_ORDER 缓存
前端轮询 purchase-result 接口 → 查到缓存 → 「抢购成功」
```

### Q3：消息会丢吗？怎么保证可靠性？（必考题）

三端回答：
- **生产者端**：开启 publisher confirm（发布确认），发送失败记录到消息日志表（项目有 `mq_message_log` 表做消息追踪）
- **Broker 端**：队列和消息声明持久化（durable），配合持久化交换机
- **消费者端**：手动 ACK，业务处理成功才 `basicAck`，失败 `basicNack` 重回队列

### Q4：说说手动 ACK 踩过的坑（项目真实踩坑案例，面试加分）

**Bug 现象**：消费者跑着跑着「停摆」，队列里消息堆积但无人消费。
**根因**：配置了 `acknowledge-mode=manual`，但 `OrderMqReceiver` 的 `@RabbitHandler` 里**没有调用 `channel.basicAck()`** → 所有消息一直处于 unacked 状态 → 达到 prefetch 上限 → 消费者不再拉取新消息。
**修复**：处理成功 `basicAck(deliveryTag, false)`，失败 `basicNack(deliveryTag, false, false)`。
**教训**：配置手动 ACK 就必须配套显式确认，否则 unacked 累积到 prefetch 上限，消费者永久停摆。

### Q5：消息重复消费怎么办？

**MQ 无法保证 exactly-once，只能做到 at-least-once + 消费端幂等**：
- 网络超时重发、消费者重试都会导致重复投递
- 项目方案：消息带 requestId，消费端先 SETNX 幂等标记，重复消息直接丢弃；DB 唯一索引兜底
- 同时消费者下单逻辑本身有「用户已购」检查，双重保障

### Q6：消息积压怎么办？

分层回答：
1. **事前**：接口入队前先查库存缓存，库存不足直接拒绝，避免无效消息
2. **事中**：提高消费速率——加大 prefetch、增加消费者并发数（`concurrency`/`max-concurrency`）、横向扩容消费者实例
3. **事后**：临时扩容消费者批量消费；积压消息分流到新队列
- **项目诚实的点**：异步削峰后瓶颈从「接口」转移到「消费速率」，入队 3944 QPS 但消费者处理能力有限——这正是排队场景的根源，面试时要主动讲这个权衡

### Q7：用户怎么知道抢购结果？（异步化后的体验问题）

- **轮询方案**（项目实现）：前端 500~600ms 间隔调 `purchase-result` 接口，消费者落单后写 USER_HAS_ORDER 缓存，轮询查到即「恭喜您，已经抢购成功！」
- 轮询开销大但实现简单；进阶方案：长轮询、WebSocket 推送、服务端延迟队列定时通知

### Q8：MQ 还能用在哪些地方？

项目里 MQ 有两个队列：
1. **orderQueue**：异步下单主链路
2. **delCache**：缓存删除兜底——延迟双删失败时，发消息让专门消费者重试删缓存，保证最终一致

## 三、缓存相关

### Q1：缓存和数据库双写一致性怎么保证？（必考题，项目 V1~V5 五连击）

项目把五种策略全部实现并压测，按演进回答：

| 策略 | 做法 | 问题 |
|---|---|---|
| **V1 先删缓存再扣库** | 删缓存 → 扣 DB | 两步之间有窗口：读请求把 DB 旧值回填缓存 → 脏数据 |
| **V2 先扣库再删缓存** | 扣 DB → 删缓存 | 业界基础策略：删缓存失败最多残留旧值，窗口极小 |
| **V3 延迟双删** | V1 + 1 秒后再删一次 | 兜底清掉窗口期回填的脏缓存 |
| **V4 + MQ 兜底** | V2 + 双删 + delCache 队列 | 连删除失败都覆盖，最终一致 |
| **V5 技术堆砌（反面）** | 乐观锁+用户校验+MQ+缓存全上 | QPS 7、RT 10 秒，性能崩塌 |

**结论金句**：业界最常用的是 Cache Aside 模式（V2：先更新 DB 再删缓存），叠加延迟双删和 MQ 兜底可达到最终一致；「架构不是越复杂越好」。

### Q2：缓存穿透、击穿、雪崩怎么解决？（必考题）

| 问题 | 定义 | 项目处理 |
|---|---|---|
| 穿透 | 查询不存在的数据，绕过缓存直打 DB | 库存这类数据一定有值；接口层先校验 sid 合法性，非法请求直接拒绝 |
| 击穿 | 热点 key 过期瞬间大量请求打 DB | 抢购场景库存是热点：预置时写入缓存 + 回源时兜底回填（Cache Fallback） |
| 雪崩 | 大量 key 同时过期/Redis 宕机 | 过期时间不设同一时刻；**缓存兜底机制**：缓存异常时降级查 DB，DB 异常返回空并记录日志 |

项目有完整的 **Cache Fallback**：缓存未命中 → 回源 DB → 回填缓存（3600 秒），保证「缓存优先、数据库兜底」。

### Q3：为什么用二级缓存 Caffeine + Redis？

- **L1 Caffeine（本地）**：纳秒级读取、零网络开销，适合超热点数据（如库存）
- **L2 Redis（分布式）**：多实例共享、容量大
- **失效同步**：通过 Redis **Pub/Sub** 广播失效消息，其他实例收到后同步清本地 Caffeine——解决「本地缓存跨实例不一致」问题
- 读路径：Caffeine 命中 → Redis 命中 → DB 回源回填

### Q4：库存缓存是准确的吗？（有深度的追问）

**诚实回答：不保证实时准确，只保证最终一致**。
- 缓存库存用于**展示和快速拦截**（卖完直接拒绝），真正的扣减以 DB 为准（锁策略保证）
- 实测缓存读 QPS **2177**，是查 DB（668 QPS）的 **3 倍**——缓存的价值是吞吐，不是精确
- 下单后立刻删缓存（V2/V3/V4 策略），下次读回源拿最新值

### Q5：缓存键怎么设计？

- 用 **枚举统一管理**（CacheKey 枚举类），避免散落魔法字符串
- 结构带业务维度：`USER_HAS_ORDER_{sid}`、`STOCK_{sid}`、`USER_HAS_ORDER_{date}_{userId}`
- 过期时间分级：库存短（秒级/分钟级）、用户已购长（当天有效）、验签 hash 3600 秒

### Q6：验签 hash 为什么存 Redis？

- hash = MD5(盐 + sid + userId)，签发后存 Redis 3600 秒
- 下单时比对请求携带的 hash 与 Redis 中的值，一致才放行
- 本质是**一次性凭证**：服务端可控失效、脚本无法伪造

### Q7（加分题）：缓存 V1~V4 压测 QPS 为什么没差别？

实测 V1~V4 QPS 都在 269~319，**差距 <20%**。
**原因**：瓶颈在悲观锁（QPS ~300），缓存清理耗时（毫秒级）相比锁等待（100~200ms）可忽略。所以缓存一致性演进**不提升吞吐，只提升正确性**——面试官若问「加了缓存为什么 QPS 没涨」，答「读路径的收益被写路径的锁串行化吞掉了」，能体现对系统瓶颈的洞察力。

## 四、数据库设计与 SQL 优化（高频，项目素材丰富）

### Q1：秒杀系统的表怎么设计的？有哪些考虑？

项目核心表设计要点：
- **stock 表**：`count`（总数）、`sale`（已售）、`version`（乐观锁版本号）——`version` 是乐观锁 CAS 的载体；`sale` 冗余累计已售，读「剩余 = count - sale」不必 SUM 订单
- **ticket 表**：`total_count / remaining_count / sold_count` 三字段冗余 + `uk_date` 唯一索引（一天一条票券记录）
- **ticket_order 表**：`uk_order_no` 唯一索引（订单号幂等兜底）、`amount` 用 **bigint 分**存储（阿里规范：金额最小单位整型）、`status` 状态机（1 待支付/2 已支付/3 已取消/4 已过期）

### Q2：唯一索引在秒杀系统里起什么作用？

**数据库层幂等的最后一道防线**：应用层（SETNX、用户已购缓存）都可能失效，但 `uk_user_date`（用户+日期）、`uk_order_id`、`uk_ticket_code` 保证数据库层面绝不重复。面试话术：「幂等不能只靠应用层，DB 唯一约束是兜底」。

### Q3：你项目里用了外键（`FOREIGN KEY ... ON DELETE CASCADE`），但阿里规范禁用外键，你怎么看？

辩证思维题：
- 阿里规范禁外键的理由：高并发下外键检查影响写入性能、级联删除有「更新风暴」风险、分库分表后外键无法跨库
- 项目 ticket 表外键是教学场景（单库、数据量小、级联删除票券时同步清购买记录很方便）
- **结论**：约束逻辑在业务层做（Service 校验 + 事务），生产环境移除物理外键、保留逻辑关系——能主动承认并解释这个权衡是加分项

### Q4：`SELECT ... FOR UPDATE` 的锁细节？

- 必须在**事务内**才生效；锁的是索引行，无索引会锁全表
- 事务范围要小：锁内只做「读库存→扣减→插订单」，不要夹带 RPC、慢查询
- 多个资源加锁顺序要一致防死锁

## 五、并发编程 & JVM（区分度所在）

### Q5：项目里线程池怎么用的？为什么不直接用 Executors？

延迟双删（缓存 V3/V4）用**命名有界线程池**（`seckill-delay-delete-`）：
- 阿里规范：`Executors` 的 Fixed/Single/Cached 线程池队列无界，高并发下可能 OOM，必须用 `ThreadPoolExecutor` 显式指定参数
- 线程命名有意义，出错时日志可回溯
- **V5 反面教材恰好是 JVM 面试题**：每次请求 `new ArrayList(10000)` → 大对象频繁分配 → GC 压力巨大 → 实测 QPS 从 300 崩到 **7、RT 10 秒**。「性能问题不一定是锁，可能是 GC」——用这个案例讲 JVM 调优非常有说服力

### Q6：JVM 参数怎么配的？

- Docker 容器内 `-Xms1g -Xmx1g`（**初始=最大**，避免堆动态伸缩引发 GC 压力）
- 生产标配 `-XX:+HeapDumpOnOutOfMemoryError`（OOM 时留现场）
- 延伸：容器内 JVM 与 cgroup 的适配（`-XX:+UseContainerSupport`），防止 JVM 看到宿主机内存导致超限被杀

## 六、分布式 ID / 票码生成（项目有专门的演进文档）

### Q7：票券编码怎么生成的？踩过什么坑？

- 格式：`T{日期}{6 位序列号}{用户后缀}{3 位随机}`
- **初版用 Redis INCR 的问题**（真实踩坑记录）：key 过期后 INCR 从 1 重新开始 → 序列号**不基于上次结果**、重启丢失、并发下可能重复
- 改进：独立 `SequenceGeneratorService`，持久化 + 连续性 + 原子性保证；`uk_ticket_code` 唯一索引兜底
- 面试延伸：**雪花算法**（时间戳+机器号+序列号，不依赖中间件）、时钟回拨问题、UUID 的缺陷（无序导致索引分裂）——项目里订单号用 UUID 也有同样的讨论点

## 七、定时任务与数据同步

### Q8：每日票数更新怎么做的？和抢购并发冲突吗？

- `@Scheduled` 每天凌晨 1 点：删除今日票券、更新后天票数、**同步清理相关缓存**（DB 与缓存一致性）
- `@Transactional` 保证更新原子性
- **面试追问点**：① 定时任务如果服务部署多实例，会重复执行——需要分布式锁或 ShedLock 抢占；② 定时更新与用户抢购同时写 ticket 表，靠 `version` 乐观锁/行锁保证不互相覆盖

### Q9：项目里 Canal 是干什么的？

`miaosha-job` 模块用 **Canal 订阅 MySQL binlog** 做增量数据同步（`getWithoutAck(1000)` 拉取 + `ack(batchID)` 手动位点确认）：
- 典型应用：**binlog 驱动缓存失效**（替代双删的终极方案，DB 变了缓存一定删）、异构数据同步（同步到 ES/数仓）
- 对比：应用层双写有失败/时序问题，binlog 订阅是「数据库自己说真话」
- 加分：讲清 `ack` 位点管理——处理成功才 ack，失败重试不丢数据

## 八、业务设计

### Q10：每人每天限购 1 张怎么实现的？

**三层**：① 接口层 Redis Set 去重（`USER_HAS_ORDER_{sid}` 快速拦截）；② 消费者侧再次校验用户已购缓存；③ DB `uk_user_date` 唯一索引兜底。面试话术：**「入口快速拦截 + 核心链路校验 + 存储层兜底」的纵深防御**。

### Q11：订单取消（24 小时）和状态机怎么设计？

- 状态机：待支付 → 已支付 / 已取消 / 已过期；取消必须校验当前状态（不能取消已支付订单）
- 状态流转用「状态图」表达（阿里规范：状态超 3 个用状态图）
- 过期扫描：定时任务批量捞「待支付且超时」订单改「已过期」，同时**回补库存**——回补的幂等处理（防止重复回补）

### Q12：匿名用户怎么设计的？

userId 默认 `-1` 表示匿名用户（无需登录体验）；类型从 String 迁移到 Long 的兼容性处理（前端默认值、接口参数、DB 字段 `bigint` 对齐）——这是「接口/数据模型演进兼容」的小案例。

## 九、代码质量与排查能力（面试官最爱的追问）

### Q13：你发现过别人代码里的什么 bug？

演进分析文档记录了 6 个真实问题，都是「代码审查」类面试题的绝佳素材：
- `new ArrayList(10000)` 死代码 → GC 压力 → 性能崩塌
- `Thread.sleep(10000)` 模拟延迟没删 → 每个请求睡 10 秒 → RT 10s
- `insertOrderRecord` 判空逻辑**写反**（`null != orderRecord` 时 return）→ 订单永远不落库
- `updateOrderRecordStatus` 条件用 `&&` 而非 `||` → 状态更新永不生效
- `e.printStackTrace()` 不规范（应打日志并带上下文）

**答题框架**：现象（压测 QPS 异常）→ 定位（jstack/日志/读代码）→ 根因 → 修复 → 沉淀（压测要看业务成功率而非 HTTP 成功率）。

## 面试「杀手锏」话术（30 秒版）

> 我做了一个秒杀抢购系统，把无锁、乐观锁、悲观锁、缓存双写五种策略、MQ 异步削峰、验签防护、分布式锁/幂等/限流/熔断全部实现了一遍，并且用 40 轮压测拿到了每个方案的真实数据。三个反直觉的结论：**① HTTP QPS 不等于业务 QPS（无锁方案 3158 QPS 但业务成功率 1%）；② 高争用下乐观锁反而不如悲观锁（业务 QPS 13 vs 328）；③ 堆砌好技术不等于好架构（V5 全都要 QPS 只有 7）。最终生产方案选型：悲观锁 + Redis 分布式锁 + MQ 异步 + 缓存双删兜底，业务成功率 94%~100%、零超卖。**
